LG-01

변경 내역 도출 로직 — N차 · N-1차 비교

확정 — 비교 방식·주체 (개발팀 협의 2026-07-15 · 07-20)

비교 방식 — 필드별 diff 설계·저장 없음. N차·N-1차 전체 데이터를 비교해 값이 달라진 항목만 추출(새 필드 자동 포함).

비교 주체 — BE가 교부 시점에 1회 비교·저장. 닷컴·하나허브·파트너포탈은 저장된 결과를 렌더만 → 3개 화면 항상 같은 값.

데이터 조달 — API에 변경 내역 필드 추가

  • As-Is — 현행 여행계약서 API는 N차(최신) 계약서 내용만 응답. 변경 내역을 받을 수단 없음.
  • To-Be — 기존 응답은 그대로 두고 “변경 내역” 필드 하나 추가.
FE 수신구분내용
계약서 내용기존N차(최신) 여행계약서 내용 — 현행 그대로
변경 내역신규BE가 미리 비교해둔 결과 배열 — 항목당 [변경 항목 / 이전 내용 / 변경 내용]

→ N-1차 원본은 FE로 내려가지 않음. 화면은 받은 배열을 표로 렌더만 → 3개 화면 값 불일치 원천 차단.

비교 로직

구분내용
■ Back-End
트리거교부상태 미교부 → 교부완료 전환(= 고객 열람) 시 1회 비교. 실제 발동 — 미교부 상태에서 예약 상세 진입 시 계약서 팝업이 자동 노출되고, 그 호출 시 BE가 교부완료로 전환(AS-01 ④). 페이지 진입만으로 발동, FE 통지 불필요.
교부완료 = 열람, 동의와는 별개 상태값(AS-01)
시점 근거교부완료 전환 = 해당 차수 내용이 확정되는 순간. 미교부 구간은 비교하지 않음(내용이 계속 바뀜).
비교 입력N차 · N-1차 여행계약서 전체 데이터 비교 (BE 내부값, FE 미전달).
처리값이 달라진 항목명 + 이전 값 + 변경 값 추출.
저장변경 내역 배열을 해당 차수에 통째 저장(새 필드 늘어도 구조 변경 불요). 확정 후 재산출 없이 재사용.
■ API 응답
응답 필드기존 N차 계약서 내용 + 신규 변경 내역 필드 (= 신규 개발) · 닷컴·하나허브·파트너포탈 공유.
화면 활용 (1)
변경 내역 표		변경 내역 배열을 SC-02 탭 / SC-03 팝업에 그대로 렌더 — 요약·생략 없이 전 건(No는 렌더 시 부여).
화면 활용 (2)
탭 노출 여부		건수 0 / 1건 이상으로 분기 — 1건 이상 탭 생성, 0건 탭 미생성. 상단에 항목명·사유 미포함.
⚠ 문구는 발송 시점(사유 값), 탭 유무는 열람 시점(비교 건수)에 결정 — 두 시점이 다르므로 유도 문구를 조건부 표현(“변경된 항목이 있는 경우”)으로 고정해 0건일 때 문구·화면이 어긋나지 않게 함(AS-02).
미적용 조건1차(N-1차 없음) → 1차형 문구 · D-2 확정 교부 → “출발 확정 안내” 고정. 둘 다 변경 내역 0건 → 탭·팝업 미노출.
재교부인데 0건재교부 요건은 발생했으나 비교 결과가 0건인 경우. 발생 경로 —
① 변동금액만 변경 : flxb*는 금액 없는 Y/N 플래그(실측 6.6)라, 이미 체크된 항목의 금액만 바뀌면 계약서 데이터가 그대로다 개발 확인 1번 결과에 좌우됨
② 노출 제외 항목만 변경 : 비교는 잡았으나 고객 노출 대상이 아니라 표 건수 0 LG-02 미정
③ 계약서 데이터 모델에 없는 요건 항목만 변경 : 프로모션·테마·현지합류 구분 등 [확인필요]
④ 원복·상계 : 미교부 구간 in-place update로 값이 되돌아옴(A→B→A)
⑤ 내용 변경 없는 수동 재교부 : 고객 요청 재발송 · 알림톡 미수신 정정
→ 재교부 문구는 그대로 유지하고 탭만 미생성. 유도 문구가 조건부 표현이라 모순 없음.
🏷 착수 시 확정 필요

① 저장 구조 — 보관 위치(차수 테이블 컬럼 vs 별도) + 1차(비교 대상 없음)일 때 값(빈 배열 / null).

② 미교부 차수 조회 — 아직 열람 안 한 차수는 비교 결과 없음. 하나허브·파트너포탈 조회 시 처리(진입점 미노출 / “고객 미열람” 안내 / 실시간 비교).

③ 비교 정확도 — AI비교 vs Data-Field 비교 방식 선택 + 정확도 기준 + 실패 시 fallback(문구 fallback + 표 미노출).

④ 상단 문구 원칙 — 고정 유도 문구, 항목명·사유 미포함. 결과는 변경 내역 표로만 전 건 노출.

⑤ D-2 교부의 변경 내역 처리 — 현재 D-2는 변경 내역 0건 고정. 다만 직전 차수가 교부완료된 뒤 변경이 생겼는데 담당자 재교부 없이 D-2에 도달하면, 고객이 본 스냅샷과 달라졌는데도 변경 내역이 노출되지 않는다. 0건 고정을 유지할지, “직전 교부완료 스냅샷 대비 0건일 때”로 좁힐지 개발 협의에서 판단.

◎ 착수 전 검토 사항 — 열람 응답 지연(latency)

트리거가 열람이라 비교가 계약서 여는 순간 발생 → 열람 자체가 느려질 수 있음. 검토안 — 동기 vs 비동기(본문 먼저 표시, 변경 내역 탭만 로딩). → 착수 전 검토, 비교 성능 실측 후 판단.

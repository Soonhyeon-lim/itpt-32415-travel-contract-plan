LG-01

변경 내역 도출 로직 — N차 · N-1차 비교

확정 — 비교 방식·주체 (개발팀 협의 2026-07-15 · 07-20)

비교 방식 — 필드별 diff 설계·저장 없음. N차·N-1차 전체 데이터를 비교해 값이 달라진 항목만 추출(새 필드 자동 포함).

비교 주체 — BE가 교부 시점에 1회 비교·저장. 닷컴·하나허브·파트너포탈은 저장된 결과를 렌더만 → 3개 화면 항상 같은 값.

데이터 조달 — API에 변경 내역 필드 추가

As-Is — 현행 여행계약서 API는 N차(최신) 계약서 내용만 응답. 변경 내역을 받을 수단이 없음.

To-Be — 기존 응답은 그대로 두고, “변경 내역” 필드 하나 추가.

FE 수신구분내용
계약서 내용기존N차(최신) 여행계약서 내용 — 현행 그대로, 변경 없음
변경 내역신규BE가 미리 비교해둔 결과 배열 — 항목당 [변경 항목 / 이전 내용 / 변경 내용]

N-1차 계약서 원본은 FE로 내려가지 않음. 화면이 두 차수를 받아 비교하는 구조가 아니라, 이미 비교된 결과만 수신.

→ FE는 비교 로직 없음. 화면은 받은 배열을 표로 그리기만 하므로, 3개 화면의 결과 불일치가 원천적으로 불가능.

구분내용
■ 백엔드 내부 — 화면에 내려가지 않는 구간
비교 주체백엔드 — 화면(FE)은 비교하지 않음
트리거교부상태 미교부 → 교부완료 전환 시점 = 고객이 계약서를 열람하는 순간. 그 전환을 트리거로 N차·N-1차 비교 1회 수행 → 저장.
실제 발동 지점(현행 AS-01 ④) — 교부상태가 미교부면 고객이 예약 상세에 진입하는 순간 계약서 팝업이 자동 노출되고, 그 계약서 호출 시 BE가 교부완료로 전환. 즉 고객의 클릭이 아니라 페이지 진입만으로 발동하며, 전환 주체가 BE이므로 FE가 열람 사실을 별도 통지 불필요.
미교부 구간에는 비교하지 않음 — 내용이 계속 바뀌므로 비교해도 곧 무효가 되기 때문
교부완료 = 열람이며 동의와는 별개 상태값(교부내역 화면에서도 교부·동의는 별도 컬럼)
시점 근거미교부 구간은 수정이 쌓이는 구간이고, 교부완료 전환 = 해당 차수 내용이 확정되는 순간. 이때 비교해야 결과가 다시 낡지 않음.
확정 이후 그 차수는 내용이 바뀌지 않으므로 → 하나허브·파트너포탈은 저장값을 계속 재사용(재산출 불요)
비교 입력N차 여행계약서 데이터 · N-1차 여행계약서 데이터 (각 차수의 전체 스냅샷)
BE가 내부적으로 읽는 값 — FE로 내려가지 않음
처리두 데이터를 비교 → 값이 달라진 항목명 + 이전 값 + 변경 값을 추출 (신규 작문 아님)
저장산출된 변경 내역 배열을 해당 차수에 저장
항목별 sub table을 설계하는 것이 아니라 비교 결과를 통째로 보관 — 새 필드가 늘어도 구조 변경 불요
■ API 응답 — 화면이 받는 것
응답 필드기존 N차 계약서 내용(변경 없음) + 신규 변경 내역 필드 (= 신규 개발)
닷컴·하나허브·파트너포탈이 같은 필드를 공유
화면 활용 (1)
변경 내역 표		받은 변경 내역 배열 → 화면정의 SC-02 변경 내역 탭 / SC-03 팝업에 그대로 렌더
항목당 [변경 항목 / 이전 내용 / 변경 내용] · 요약·생략 없이 전 건 표기(No는 렌더 시 부여)
화면 활용 (2)
탭 노출 여부		배열의 건수(0 / 1건 이상)로 탭·문구 분기
1건 이상 → [변경 내역] 탭 생성 + 상단은 “탭에서 확인해 주세요” 유도 문구 고정 · 0건 → 탭 미생성
상단 문구에 변경 항목명·사유를 넣지 않음 — 사유 요약 로직 불필요(2026-07-20 변경)
미적용 조건1차(최초) 교부는 N-1차가 없으므로 비교 대상 없음 → 1차형 문구 · D-2 확정 교부는 사유 = “출발 확정 안내” 고정
두 경우 모두 변경 내역 0건 → 탭·팝업 미노출
🏷 착수 시 확정 필요

① 저장 구조 — 변경 내역을 어디에 어떤 형태로 보관할지(차수 테이블 내 컬럼 vs 별도 보관) 및 1차(비교 대상 없음)일 때의 값(빈 배열 / null) 확정.

② 미교부 차수의 변경 내역 조회 — 고객이 아직 열람하지 않은 차수는 비교 결과가 아직 없음. 이때 하나허브·파트너포탈에서 변경 내역을 조회하면 어떻게 할지 확정 필요(진입점 미노출 / “고객 미열람” 안내 / 해당 건만 실시간 비교).

③ 비교 정확도 — 비교 정확도 기준과 비교 실패 시 fallback 확정(문구 fallback + 표 미노출 처리).

④ 상단 문구 원칙 — 상단은 고정 유도 문구이며 변경 항목명·사유를 넣지 않음. 비교 결과는 오직 변경 내역 표(출력 1)로만 전 건 노출 → 상단·표 사이에 내용 불일치가 생길 여지 자체를 없앰.

◎ 추가 검토 — 열람 응답 지연(latency)

트리거가 열람이므로 비교가 계약서를 여는 그 순간 발생. 비교에 시간이 걸리면 계약서 열람 자체가 그만큼 느려질 수 있음.

검토안 — 동기(비교 완료 후 응답) vs 비동기(계약서 본문 먼저 표시, 변경 내역 탭만 로딩). 착수 전 필수 결정은 아니며, 비교 성능 실측 후 판단.

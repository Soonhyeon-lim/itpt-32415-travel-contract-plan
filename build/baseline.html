배경 및 목적

◎ 배경

매월 100건 이상의 여행계약서 단순 문의가 접수로 고객 불편 증가 및 직원 업무 효율 감소. 이를 해소하기 위해 개선 진행

  • 여행계약서 총 2회(1차 계약서, 2차(확정) 계약서) 자동 교부가 진행되나, 2차 교부 시(+재교부) 사유에 대한 안내가 부족. VOC 증가
  • 알림톡을 통해 교부 안내가 나가지만, 닷컴 로그인 페이지로 전환 중. 회원 여부가 불명확하거나 회원 정보 오입력으로 VOC 증가
  • 여행계약서에 변동 금액이 명확히 표시되지 않고 있어 고객이 지불한 금액이 명확히 나오지 않고 있음.
  • 반복적인 문의 처리로 인해 고객 불편이 증가하고, 직원 업무 부담. 이를 개선하여 고객 편의 및 업무 효율 증대 목적

① 계약서 차수·변경 내역 표기

D-2 및 계약서 내 항목 변경으로 인한 재교부 가능성 안내. + 이전 계약서와 다른 항목 탭으로 분리하여 안내

① 상단 문구 — 계약서 상단에 [N차 여행계약서]와 함께 발송 상황에 따라 문구 3가지(최초 발송 / 출발 확정 / 변경 재교부)로 안내. 변경 재교부일 때는 “변경된 항목은 [변경 내역] 탭에서 확인해 주세요”로 유도하고, 상단에 변경 항목을 나열하지는 않는다.

② 변경 내역 탭 — 직전 계약서 대비 바뀐 항목이 있을 때만 [계약서 / 변경 내역] 탭이 생기고, 표로 어떤 항목이 무엇에서 무엇으로 바뀌었는지 표기.
내용 변경 없이 차수만 변경된 경우 '변경 내역' 탭 미노출.

고객이 “또 왔네”가 아니라 “이게 바뀌어서 왔구나”로 읽히게 하는 것이 목적.

③ 일정표 선택관광·쇼핑 단순 표기

교통·숙박·식사를 일정표에 표시하는 것과 같은 방식.

④ 하나허브 여행계약서 교부내역 — 개인추가경비 합산값 · 변경 내역

As-Is — 고객이 보는 “개인추가경비 N원”과 같은 값을 상담원이 바로 확인할 방법이 없음(현재 불가 확인).

To-Be — 하나허브 여행계약서 교부내역 메뉴에도 같은 합산값을 표시하고, 변경 내역은 별도 팝업으로 확인.

변경 내역 팝업은 고객 화면(①)의 ‘변경 내역’ 탭과 같은 것을 그대로 사용 — 같은 데이터로 같은 표(No / 변경 항목 / 이전 내용 / 변경 내용)를 보여준다.

→ 개인추가경비는 개선 ②와, 변경 내역은 개선 ①과 반드시 같은 값 — 고객이 보는 것과 상담원이 보는 것이 어긋나면 그 자체가 새 CS.

⑤ 여행계약서 조회 진입 페이지 검토 필요

As-Is — 알림톡 “여행계약서 확인”을 눌렀는데 (앱 없음/로그인 안 됨) 로그인 페이지를 거쳐 “비회원 예약조회” 화면으로 도착. 계약서를 보러 왔는데 제목이 “예약조회”라 “여기가 맞나?” 하고 이탈 (CS 1위 진입 장벽의 잔여분).

To-Be — 계약서를 보러 들어온 고객에게는 화면 제목이 “여행계약서 조회”로 보이게 하고, 여행계약서는 패키지 상품만 해당하므로 호텔·항공 탭 없이 패키지 탭만 보이게 한다.

포인트 4가지 : ① 예약번호는 지금처럼 자동으로 채워짐(고객은 이름·휴대폰번호만 입력) ② 계약서로 들어온 경우에만 제목·탭이 바뀜 ③ 조회 성공 → 예약 상세로 이동(계약서 팝업은 그 화면에서 노출 — 현행 그대로) ④ 비회원 전용(회원은 로그인 후 마이페이지에서 확인).

닷컴 직접예약 건 D-2 발송 포함 확인 항목

현행 — 닷컴에서 직접 예약한 건은 최초 알림톡이 나가지 않음(예약내역에서 바로 확인하는 구조).

요구사항 — 이 건들도 출발 2일 전 최종 확정본 발송 대상에 포함 → 모든 고객이 출발 전 확정된 계약서를 받도록. 새로 만드는 기능이 아니라 기존 발송에 포함되는지 확인하는 건이라 개선 번호에서는 제외.

LG-01

변경 내역 도출 로직 — N차 · N-1차 비교

2026-07-15, 개발팀 협의

변경 항목을 필드별로 일일이 설계·저장하지 않는다. N차·N-1차 여행계약서 전체 데이터를 비교해 값이 달라진 항목만 추출 — 새 문장을 작문하는 것이 아니라 두 데이터의 차이값을 뽑아내는 방식.

기존 방식이었다면 변경 항목별 sub table + 필드별 diff 로직을 손으로 설계해야 했으나, 이 방식은 그것이 불필요해져 공수·확장성 부담이 크게 감소. 새 필드가 추가돼도 비교 대상에 자동 포함.

⚠ 아키텍처 변경 — 비교 주체를 FE → BE로 (2026-07-20)

문제 — 비교를 화면(FE)에서 하면 닷컴·하나허브·파트너포탈 3곳이 각자 비교하게 된다. ① 같은 계약서인데 화면마다 결과가 달라질 수 있고(“고객 화면 = 하나허브 동일 값” 원칙이 깨짐) ② 비교가 3중 수행되어 비용·지연이 늘며 ③ 항목명 매핑·노출 제외 규칙을 3벌 관리해야 한다.

결정 — BE가 교부 시점에 1회 비교하고 그 결과를 저장한다. 각 화면은 저장된 변경 내역을 받아 렌더만 한다 → 3개 화면이 무조건 같은 값을 본다.

데이터 조달 — API에 변경 내역 필드를 추가한다

As-Is — 현행 여행계약서 API는 N차(최신) 계약서 내용만 응답한다. 변경 내역을 받을 수단이 없음.

To-Be — 기존 응답은 그대로 두고, “변경 내역” 필드 하나를 추가한다.

N-1차 계약서 원본은 FE로 내려가지 않는다. 화면이 두 차수를 받아 비교하는 구조가 아니라, 이미 비교된 결과만 받는다.

검토안 — 동기(비교 완료 후 응답) vs 비동기(계약서 본문 먼저 표시, 변경 내역 탭만 로딩). 착수 전 필수 결정은 아니며, 비교 성능 실측 후 판단.
